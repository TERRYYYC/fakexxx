## S2-B — Hook runner readiness

冻结 bench APK 的 manifest 由记录者独立读取，确认：

- package 为 `name.caiyao.fakegps.bench`；
- `RUN_HOOK_ACCEPTANCE` permission 的 protection level 为 `signature`；
- `name.caiyao.fakegps.probe.HookAcceptanceActivity` 显式绑定该 permission。

canonical `test-hook.sh --acceptance-readiness` 的冻结输出为：

```text
VERIFIED preflight.device api=35 awake unlocked rooted
VERIFIED acceptance.gate signature permission denies unprivileged start
VERIFIED acceptance.component resolved and fail-fast aborted without payload
READINESS_PASS name.caiyao.fakegps.bench/name.caiyao.fakegps.probe.HookAcceptanceActivity is the signature-gated bench acceptance component; no transaction entered
RUNNER-EXIT=0
```

紧邻的原始 logcat 为：

```text
{"sessionId":"unparsed","state":"aborted","error":"java.lang.IllegalArgumentException: missing acceptance_session_id"}
```

两份 S2-B 文件均无 `"state":"published"`。candidate 上的 runner 原文只有在 Stage 1 收到
permission denial 且输出点名 bench permission、Stage 2 root 无 payload 启动成功并观测到上述 abort、
同时无 published 时才会输出 `READINESS_PASS`。本次判据对象明确是 `HookAcceptanceActivity`，
不是 S1 错用的 `ComposeActivity`。

原包没有保留 Stage 1 `am start` 的完整 denial stdout/stderr，只保留 canonical runner 的 VERIFIED
终态；这是 evidence-validity 要审的透明性限制。记录者仍把 readiness predicate 记为 PASS，因为
exact candidate 的 hard-fail runner、冻结 APK manifest、Stage 2 原始 abort、负断言与 exit=0 形成
一致链条。这个 PASS 只关闭 §3.3-3 的事务外 readiness，不等于完整 Hook §G 或 G2 PASS。
